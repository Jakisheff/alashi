# Epoch 2 donkey risk: source contract (candidate)

Status: source candidate only. The program is not upgraded; no epoch-2 Game, paid oracle request, or live result has been verified. This document describes the intended wire for runner and frontend integration.

Epoch `2` inherits the epoch-1/90s market, laws, credit, shuttle, hard currency, license and settlement rules. It changes only donkey buying. Epochs `0` and `1` retain `BuyDonkey` and the historical `donkey_bought` event: one good for one in-game PESO, guaranteed.

In epoch 2, `AttemptDonkey` accepts one Action-phase attempt in rounds 1–5. It charges `5 * PESO` (in-game cash) and consumes the faction's Action before any outcome exists. An independently verified later draw succeeds with probability 3/5 and credits five goods, or returns zero goods with probability 2/5. An oracle abort is a distinct terminal outcome: zero goods, no random draw claim. There is no refund or same-turn retry in either zero-goods case. The ordinary Market purchase is still guaranteed at the current market price. Program preconditions reject before debit/stamp if the phase/round, cash, alive/acted state, inventory capacity, or oracle baseline is invalid.

## Program accounts and ordering

`Initialize(epoch=2)` requires Switchboard entropy mode. Before any Join, the admin calls `InitDonkeySource(round, recent_slot)` once for each of the six rounds. Each call derives the source PDA `[b"donkey-source", game, round]` and source authority PDA `[b"donkey-oracles", game]`, then invokes the pinned devnet provider's `RandomnessInit` with those two PDA signers and the admin as payer. The provider creates the source, escrow and LUT; this is a funded operator step and is not automatic in a Game. `ConfigureDonkeyOracles` then runs before any Join: `admin` signer, `game` readonly, canonical authority/config PDA init writable, `system_program`, followed by exactly six source PDAs and six selected provider Oracle accounts in round order. The config freezes source keys, selected Oracle keys, queue and authority; each source must still be uncommitted and unrevealed. Epoch-2 `Join` adds that canonical config PDA as its one readonly remaining account and rejects a missing or invalid config before transferring the entry fee. Legacy Join accounts are unchanged. An unconfigured empty Lobby can still time out and abort.

`AttemptDonkey` accounts: `player` signer, `game` readonly, `faction` writable, canonical config PDA writable, configured current-round source readonly. The source must still be uncommitted and unrevealed when the fee and Action are committed. At the Action deadline, the operator calls **Alashi `Advance(Action→Law)` only**. Its remaining accounts are the complete faction set, writable config PDA, writable current-round source PDA, queue, writable preselected Oracle account and executable provider program. Alashi signs a single provider `RandomnessCommit` CPI with its config PDA. It verifies the post-CPI source has `seed_slot == transaction Clock.slot - 1`, strictly after the last accepted attempt slot, is unrevealed, and names the frozen queue/authority/Oracle. It then pins the source and slot in Game and sets an irreversible per-round commit bit. A failed Advance rolls back the CPI. Epochs 0/1 keep their historical previous-slot validation and account layouts. Neither the runner nor a caller can invoke a generic Alashi re-commit path. For epoch 2, the operator passes a provider-signed gateway reveal proof to **Alashi `RevealDonkeyLaw(signature[64], recovery_id, value[32])`**. Its fixed accounts are crank signer/payer, writable Game, writable pinned source, frozen Oracle, frozen queue, writable stats PDA, SlotHashes, System Program, writable source escrow ATA, SPL Token, native mint, provider State and executable provider; remaining accounts are writable config PDA then every due writable faction in ticket order. Alashi signs a provider `RandomnessReveal` CPI with the config PDA and resolves Law and every due ticket in that same instruction/slot. The deployed provider IDL requires the source authority to sign reveal, so the obsolete external provider reveal plus Alashi `RevealLaw` bundle cannot authorize the config PDA. The provider verifies the gateway proof; failure of its CPI or any ticket validation rolls the whole transaction back. Legacy epochs retain `RevealLaw`. All due tickets resolve atomically, using the full value and a domain-separated exact 3/5 mapping. A terminal phase abort marks every due ticket technically aborted without goods; it does not report a 2/5 loss. If no valid commitment reaches Action→Law, any caller may pass the complete faction set and canonical config PDA (without a source) to `Advance` at or after the Action deadline plus a fixed 30-second grace. This is a mandatory cutoff: from that instant epoch 2 rejects source-backed commit+Advance; only the no-randomness technical-abort path remains. It resolves every paid ticket as a technical outcome, cannot mint goods or enter Law, and enables the normal entry-fee refund path. Earlier calls and legacy epochs remain strict.

The old external `commitIx` plus `Advance` and external `revealIx` plus `RevealLaw` tool wires are incompatible with this candidate. The bots host may initialize/configure sources only after a separately reviewed operator budget and must defer epoch-2 Action→Law and reveal to the updated Alashi-CPI crank. An executable operator crank, provider setup and funding, and a real devnet roundtrip are separate release gates. No normal runner may choose the draw or substitute a source. Provider withholding can still end in a technical abort; no live fairness claim follows from the local provider Init/Commit CPI plus synthetic reveal fixtures.

An attempt accepted in slot S cannot be committed before slot S+2 because the provider uses the previous slot and the committed seed must be later than every paid attempt. The fixed Action grace still applies.

## Anonymous public projection

Existing `GET /chain/devnet/games/<GamePDA>` is the only public read. It requires no owner wallet/cookie. `game.epoch` is numeric `2`. The event decoder adds only these confirmed events; the envelope already supplies canonical `id = "<signature>:<log_index>"`, `signature`, numeric `slot`, `log_index`, and `block_time`:

```json
{"type":"donkey_attempted","game":"<GamePDA>","faction":"<FactionPDA>","round":2,"fee":"5000000","id":"<signature>:<log_index>","signature":"<signature>","slot":123}
{"type":"donkey_resolved","game":"<GamePDA>","faction":"<FactionPDA>","round":2,"success":true,"goods":5,"fee":"5000000","reason":0,"id":"<signature>:<log_index>","signature":"<signature>","slot":124}
```

The examples above are schema examples, **not production events**. `reason=0` means a verified draw: `success=true,goods=5` is a win; `success=false,goods=0` is an empty draw. `reason=1,success=false,goods=0` means technical terminal oracle abort and does not imply the 40% draw occurred. An accepted attempt without a later resolution is pending only while confirmed history remains complete enough to support that conclusion. Never fabricate outcomes from timeout, partial history, UI animation, or private owner wishes. Historical `donkey_bought` remains a separate legacy event; do not reinterpret it as a risk attempt.

Frontend and runner adapters should key receipts by public Game/Faction/round and canonical event ID/signature/slot, and should distinguish pending, verified win, verified empty and technical abort. No synthetic fixture is a public Game event.
