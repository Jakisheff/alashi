# Архитектура проверки стратегий агентов в alashi

Статус: проектное решение для пилота, 07.09.2026.

## Цель

<!-- heading boundary -->

Слой проверки отвечает на один вопрос: помогло ли изменение агента принимать решения в alashi при тех же правилах и соперниках.

Слой не меняет правила игры, не разрешает агентам писать код и не делает объяснение модели источником истины. Движок принимает или отклоняет действие, сохраняет событие и рассчитывает результат.

Главный результат пилота: оператор видит, где две версии приняли разные решения, как это повлияло на партии и стоит ли сохранять изменение. Это материал решения оператора, а не доказательство общего превосходства версии.

## Границы системы

```text
Внешний оператор
      |
      v
Конфигурация эксперимента -----> Harness сравнения
      |                                |
      |                                +--> evalgame --> alashi-rules
      |                                |                  |
      |                                |                  +--> партии и события
      |                                |
      |                                +--> адаптер baseline/candidate
      |                                      (JSON stdin/stdout)
      v
Пакет происхождения и отчёт <----- cases, evidence, manifest
```

`alashi-rules` остаётся центром правил. `evalgame` запускает изолированную локальную партию. `compare_agents.py` меняет только одну сторону сравнения, ротирует места и объединяет результаты. Адаптер не получает полномочий менять состояние напрямую.

HTTP-арена и Solana-программа остаются отдельными режимами. Результат локального eval не является HTTP-событием и не является ончейн-доказательством.

## Слои и зависимости

| Слой | Ответственность | Не должен знать |
| --- | --- | --- |
| Правила | Допустимые действия, цены, законы, голоса, settlement | HTTP, LLM, промпт, стоимость вызова |
| Симулятор | Переходы партии и детерминированный replay | Провайдера модели |
| Eval harness | Парные условия, места, таймауты, fallback, артефакты | Смысл стратегии оператора |
| Адаптер | Перевод наблюдения в действие и возврат JSON | Скрытые поля состояния и внутреннюю логику settlement |
| Аналитика | Первое различие, выплаты, события после закона, диагностика | Причину, которой нет в журнале |
| Отчёт | Ссылки на события; ограничения; решение оператора | Непроверяемый рассказ модели |

Зависимости направлены внутрь: адаптер и отчёт зависят от схемы наблюдения и событий; правила не зависят от них.

## Контракт одного решения

Запрос версии 2 содержит `schema_version`, случайный `match_id`, `decision_index`, `phase`, `rules`, `observation` и `history`. `match_id` идентифицирует запуск внутри harness. Seed сохраняется в результатах harness, но не входит в JSON адаптера.

Ответ содержит действие и допустимые параметры. Неверный JSON, таймаут или выход процесса превращаются в явный `pass` и сохраняются как fallback. Отказ правила и ошибка вызова являются разными полями.

Наблюдение является проекцией `Obs`, а не полным состоянием. Проекция фиксируется в схеме и версии протокола. Для текущего eval она уже, чем HTTP API эпохи 90-х: отдельные балансы валюты и векселей не передаются. Поэтому выводы относятся к этой проекции.

## Данные и происхождение

Система записи эксперимента состоит из четырёх частей:

| Артефакт | Содержимое | Проверяет |
| --- | --- | --- |
| `cases/` | Полные партии и трассы решений | Что реально произошло |
| `evidence.json` | Эпизоды после принятых законов и указатели на события | Где различались решения |
| `manifest.json` | Конфигурация, версии схем, хэши файлов | Какие материалы вошли в прогон |
| `source.zip` | Код движка; адаптера; перечисленные файлы | Как собрать тот же эксперимент |

До внешнего пилота в manifest нужно добавить пакет происхождения: запрошенный ID модели, возвращённую версию провайдера, настройки генерации, версию промпта, версию адаптера и заявленный `cost_usd`. Если провайдер не сообщает значение, оно сохраняется как неизвестное.

Хэш подтверждает целостность сохранённого файла. Он не удостоверяет личность модели, оператора или независимость запуска. Побайтовый replay относится к движку и сохранённым действиям; новый облачный вызов может дать другой ответ.

## Модель доверия и наблюдения

Есть два допустимых режима.

| Режим | Условие | Что можно утверждать |
| --- | --- | --- |
| Проверенный адаптер | Оператор подтверждает код и его доступ к данным | Сравнение в оговорённой доверительной модели |
| Недоверенный адаптер | Процесс изолирован; seed и секреты недоступны | Сравнение с технически проверенной границей наблюдения |

Сейчас локальный процесс запускается с правами пользователя и может читать конфигурацию, результаты прошлых партий и исходники. Удаление `game_seed` из запроса закрывает прямую утечку JSON, но не заменяет изоляцию. Для недоверенного кода нужны отдельный рабочий каталог, минимальные права чтения, закрытая конфигурация seed и сетевые ограничения.

Перед пилотом проводится аудит каналов:

1. проверить поля JSON и `history` на скрытые значения;
2. проверить доступ адаптера к файлам и переменным окружения;
3. проверить, что парные прогоны не оставляют друг другу seed и результаты;
4. отдельно проверить HTTP и Solana, потому что у них разные границы наблюдения;
5. записать найденные каналы как ограничения, а не исправлять их риторикой отчёта.

Свежий случайный `u64`, создаваемый harness (`"seeds": "auto"` в compare_agents), исключает заранее известный список seed. Он не защищает от адаптера, который читает файлы. Вывод seed по наблюдениям проверен тестом tools/test_seed_inference.py: низкоэнтропийные seed восстанавливаются по картам законов, восстановление криптографического u64 по наблюдениям одной партии не показано.

## Дебриф и причинность

Автоматический отчёт отвечает на наблюдаемые вопросы:

- в какой партии и на каком решении версии разошлись;
- какое наблюдение было доступно агенту;
- какое действие принял движок;
- какие события последовали;
- как изменились выплата и место.

Формулировка по умолчанию: «версии различались в решении X; в этой партии после него произошли события Y и результат составил Z». Формулировка «X стало причиной победы» требует отдельного ветвящегося replay с сохранённой трассой и явно обозначенным контрфактическим экспериментом.

Модель может предложить текстовое объяснение, но оно не добавляется в evidence без ссылки на журнал. Отсутствующие контрфактические выплаты не восстанавливаются из предположения.

## Тонкий срез пилота

Первый эксперимент не добавляет переговоры, память между партиями или компилятор законов.

1. Оператор фиксирует одну гипотезу стратегии до запуска.
2. Baseline и candidate получают одинаковые seeds и ротацию мест; соперники те же.
3. Проводится аудит наблюдений и доверительной модели.
4. В manifest фиксируются модель и версия; настройки; промпт; адаптер; стоимость.
5. Запускается серия отложенных партий, не использованная для подбора гипотезы.
6. Отчёт показывает различия решений и результатов.
7. Оператор решает, оставить ли изменение; решение записывается отдельно от численного результата.

Контрольные стратегии `greedy`, `random`, `tactical` остаются контрольной группой. Проигрыш флагманской модели контрольной стратегии является результатом, а не ошибкой измерения.

## Мандат и будущие контуры

Зафиксированная гипотеза стратегии и компилятор ограничений являются разными системами.

Гипотеза стратегии хранится как текст до партии и проверяется по действиям. Она не ограничивает движок и не меняет объект сравнения.

Компилятор мандата переводит текст в конечный набор параметров, показывает тестовые сценарии с фактическими реакциями и добавляет ограничитель перед движком. С этого момента сравнивается система «модель плюс ограничитель». Решение требует отдельной схемы, тестов противоречий и отчёта о случаях, когда ограничитель изменил ответ модели.

Компилятор законов строится после пилота. Он принимает инициативу, переводит её в конечные параметры закона, валидирует схему и отдаёт карту на обычное голосование. Произвольный код и произвольная физика в игру не добавляются.

Исполняемые сделки M9 и M10 остаются игровыми действиями. Они проверяют выбор условий и последствия принятия сделки. Они не являются отдельным доказательством надёжности необязательных обещаний.

## Отложенные решения

| Идея | Причина отсрочки | Условие возврата |
| --- | --- | --- |
| Межпартийная память отношений | Нужны хранение идентичности и тест без истории | Пилот покажет, что оператору не хватает памяти внутри партии |
| Наследование законов между партиями | Меняет экспериментальную единицу и усложняет причинность | Есть измеримая задача для лиги, а не только зрелищный эффект |
| Двухуровневый мозг | Не доказано, какие решения можно безопасно маршрутизировать в дешёвую модель | Парные прогоны покажут одинаковое качество при меньшей стоимости |
| Ветвящийся replay | Требует определения контрфактической ветки и ограничений вмешательства | Пилот выявит решение, для которого описания событий недостаточно |
| Соревнование недоверенного кода | Нужна изоляция процесса и секретов | Появится внешний участник, которому нельзя доверить локальный доступ |

## Критерии готовности пилота

- [ ] Наблюдения адаптера перечислены и проверены для выбранного режима.
- [ ] Seed не входит в запрос, а канал файлового доступа явно классифицирован.
- [ ] Manifest содержит пакет происхождения модели и адаптера.
- [ ] Baseline и candidate прошли одинаковые seeds и ротацию мест.
- [ ] Отчёт ссылается на события и отделяет описание от причинного вывода.
- [ ] Стоимость неизвестных вызовов не подменяется нулём.
- [ ] Решение оператора записано отдельно от статистического результата.
