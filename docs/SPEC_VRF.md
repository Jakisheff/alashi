## 1. Выбор провайдера

**Switchboard On-Demand.** Обоснование по фактам разведки, не по вкусу:

1. Модель commit-reveal = pull, не push. Наша архитектура уже permissionless-кранк
   (advance); reveal-транзакцию приносит тот же кранкер — не нужен отдельный
   listener-сервис и нет риска «оракул не дозвонился в наш callback».
2. Живая документация 2026 + официальный репо примеров + свежий сторонний гайд.
   У ORAO последний релиз SDK — 05.2025, активность ниже.
3. TEE + слэшинг стейка $SWTCH — проверяемая честность, это то, что мы
   обещаем жюри и аудиту.
4. Вся отрасль (RECON §A/E) при реальных деньгах сходится на Switchboard.

ORAO остаётся запасным планом при отказе по цене/uptime [П1,П3]: их CPI-модель
(запрос → ноды пишут результат в randomness-аккаунт → читаем) вписывается в ту
же схему состояний ниже, меняется только провайдерский слой.

## 2. Изменения в аккаунтах

Новых PDA НЕ вводим. Хранение — в существующем Game (конституция: менять
периферию, не ядро):

- `entropy_mode: u8` — 0 = slot-hash (dev/мелкие банки), 1 = Switchboard.
  Выбирается при `initialize` и неизменен всю партию. Режим — свойство партии,
  а не глобальный флаг программы: старые и новые партии сосуществуют.
- `vrf_account: Pubkey` — адрес Switchboard randomness-аккаунта текущего
  раунда (пересоздаётся на каждый Law-раунд).
- `commit_slot: u64` — слот коммита, для политики свежести reveal.
- `vrf_retries: u8` — счётчик повторных коммитов (для timeout-логики).
- `vrf_spent: u64` — фактические расходы на VRF за партию (для компенсации).

Randomness-аккаунт Switchboard — их PDA (`sb.Randomness.create`), создаётся
кранкером, программа его только читает и верифицирует. Bank-PDA не меняется:
VRF не участвует в деньгах, только в вытяжке карты.

## 3. Флоу транзакций

Ключевой тайминг-факт: фаза Law у нас длится phase_duration (15–30+ сек),
оракулу Switchboard нужен 1–2 слота. Голосование и ожидание энтропии идут
ПАРАЛЛЕЛЬНО — даунтайма ноль.

```
advance (Action→Law), mode=1:
  1. elect_president (как сейчас)
  2. commit: кранкер создаёт/передаёт randomness-аккаунт Switchboard,
     программа запоминает vrf_account + commit_slot, law_card = NO_LAW
     (карта ЕЩЁ скрыта — слепая колода сохранена буквальнее, чем сейчас)

reveal_law (НОВАЯ permissionless инструкция, mode=1, фаза Law):
  1. любой приносит результат оракула (получен через Crossbar off-chain)
  2. программа верифицирует через Switchboard contract
     (RandomnessAccountData, политика свежести seed_slot)
  3. seed = result; law_card = draw_law_index(seed, mask) — карта открыта
  4. событие LawDrawn

vote / veto: разрешены только если law_card != NO_LAW (после reveal)

advance (Law→Next), mode=1:
  1. require law_card != NO_LAW — если не раскрыто, см. timeout §4
  2. tally → apply law → следующая фаза (как сейчас)
```

Кто вызывает: commit — любой кранкер (наш бот уже кранкает advance);
reveal — он же (получение randomness у Crossbar — один HTTPS-запрос бота).
Клиентский код LLM-бота и жюри-фронт не меняются: они читают law_card как раньше.

## 4. Fallback и edge cases

- **Reveal не пришёл.** Таймаут = 25 слотов (~10 с) после commit. Любой кранкер
  делает retry: новый commit (vrf_retries + 1). Максимум 3 retry.
- **Кворум не собрался за фазу.** При mode=1 фофол на slot-hash ЗАПРЕЩЁН
  (партия создана под реальные деньги — понижать гарантию нельзя). Вместо этого:
  phase_ends_at продлевается на phase_duration при каждом retry; после 3-го
  неудачного — партия переходит в фазу Aborted: settle_refund возвращает взносы
  минус фактические vrf_spent и комиссии. Deadman switch не нужен третьей
  стороне: refund — тоже permissionless кранк.
- **Гибридный режим.** mode выбирается при initialize по правилу: банк ≤ порога
  (константа MAINNET_VRF_THRESHOLD, ~$100) → слот-хэш разрешён; банк выше →
  программа ОТКАЗЫВАЕТСЯ стартовать в mode=0 (require на initialize). Devnet
  и локальный валидатор навсегда в mode=0 — скорость разработки не страдает.
- **Манипуляция кранкером.** Кранкер выбирает момент commit — классическая
  атака «выбери выгодный seed». Защита Switchboard: результат функции от
  commit'а оракула, а не кранкера; freshness-политика (seed_slot == slot−1)
  не даёт выбирать из старых результатов. Дополнительно: commit делает тот же
  кранкер, что и advance (одна транзакция) — окно выбора исчезает.

## 5. Стоимость

- Запрос на партию: 6 раундов × 1 commit+reveal (карта одна на Law-фазу).
- Кто платит: кранкер платит комиссии и fee оракула [П1 — сумма уточняется],
  компенсация — из банка ДО дележа: в settle pot = bank − reserve − vrf_spent
  (vrf_spent фиксируется по факту). Альтернатива, если fee оракула окажется
  значимой: при join добавка vrf_deposit = 6 × VRF_PRICE, остаток возвращается
  в settle. Решение — после уточнения [П1].
- Порядок величин для решения: 12 доп. транзакций на партию ≈ комиссия
  ~0.00006 SOL при 5000 лампортов за сигнатуру — на фоне рейка 5% с банка
  $100+ это шум; риск только если oracle fee окажется > $0.01/запрос.

## 6. Migration path (без даунтайма)

1. Крейт `logic.rs` уже содержит `draw_law_index(seed, mask)` — чистая функция.
   Вся миграция = замена источника seed (slot-hash → reveal-инструкция).
   Интерфейс не меняется: это подтверждает, что конституция (ядро) не тронуто.
2. Новые инструкции (reveal_law, settle_refund) и поля Game добавляются в
   программу; старые аккаунты не мигрируются — mode=0-партии доживают сами.
3. Выкат: devnet mode=0 (регресс: старые тесты зелёные) → спайк mode=1 на
   devnet [П3] → аудит новых инструкций → mainnet: новые партии >$100 только
   mode=1, мелкие — mode=0 до полного перехода.
4. Откат: feature — сам entropy_mode; откат = просто не создавать mode=1
   партии. Программный даунтайм не нужен.
