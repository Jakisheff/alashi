# Работа клиента задаёт границы изменения

Решение Амира, 26.10.2026: применять к ALASHI логику последовательной разработки, разобранную на Family & Friends Store. Начальная точка: результат конечного клиента. Этот документ задаёт порядок работы разработчика; новые возможности продукта он не объявляет реализованными.

```text
Результат человека → его задача → сценарий использования
→ правила и состояния → подходящий исполнитель → проверка → решение человека
```

## Как работать над изменением

Перед существенной правкой опиши нужный человеку результат в конкретной ситуации. Найди существующий сценарий и его владельца в коде. Для продуктовой постановки используй канон AJTBD/NMT Амира; обычный ремонт привязывай к действующему поведению. Отдельный документ нужен, если постановка новая или неоднозначная.

Свяжи существенное правило с местом исполнения и доказательством. Например: «закрытая инструкция владельца отсутствует в публичном ответе» требует проверки выдачи API. Скрытого поля на экране недостаточно.

Определи переход состояния и значимые отказы. Для операции с внешними эффектами укажи результат прерывания и повторного вызова. Сохраняй существующие ограничения авторизации и обязательные проверки из [AGENTS.md](../../AGENTS.md).

Передавай агенту клиентский результат и конкретный участок сценария, разрешённые файлы и критерий приёмки. Ведущий агент принимает части по целому сценарию. Самостоятельная работа нескольких агентов не означает, что интеграция проверена.

## Применение к проверке человеческой идеи

Это целевой способ организации новых сценариев, target. Текущее частное исполнение описано в [COMPARISONS.md](../../tools/agent-bootstrap/COMPARISONS.md).

| Звено | Что должно быть явно задано | Проверка или граница |
| --- | --- | --- |
| Задача человека | Какое действие он выберет по результату, какие альтернативы доступны сейчас | Сценарий содержит решение, которое можно принять, включая отсрочку из-за нехватки данных |
| Гипотеза | Предлагаемое человеком изменение и ожидаемое различие | Предсказание и критерий решения фиксируются до подтверждающего опыта; разведочный поиск отмечается отдельно |
| Условия | Версия правил, исходные данные, сравниваемые варианты и ограничения ресурсов | Известно, какие условия общие и что изменяется; протокол определяет допустимость вывода |
| Исполнение | Модель, программа или агент, выбранные под задачу | Для расчёта очереди подходит вычислительная модель; LLM нужен только при определённой роли. Настоящие правила движка используют там, где проверяется игра |
| Отказ | Какие результаты и расходы уже возникли, можно ли продолжить тот же опыт | Неопределённый ответ не превращается незаметно в новый оплачиваемый запуск. Неизвестная стоимость не записывается как ноль |
| Вывод | Наблюдаемое различие, ограничения модели и основание решения владельца | Корректность исполнения, эффект в модели и реальный эффект различаются. Одного успешного прогона недостаточно для устойчивого улучшения |
| Повторное использование | Какие части сценария разрешено открыть другим людям | Закрытые данные и инструкции не публикуются автоматически; право на использование и происхождение материала известны |
| Интерес к формату | Хотел ли человек продолжить и вернулся ли со своей следующей задачей | Измеряется отдельно от качества решения и готовности платить |

Малое изменение ограничивает вмешательство, но не исключает последствий в других частях системы. Для опыта сохраняй выбранные условия; для разработки прослеживай затронутых потребителей. Эти две проверки решают разные задачи.

## Что уже есть и чего пока нет

Observed по чтению текущей ветки: приватное сравнение содержит вопрос владельца и критерий решения, фиксирует одно изменение инструкции, разделяет журналы и поддерживает продолжение попытки. [Запись приёмки](../ops/HUMAN_COMPARISON_20261025.md) описывает прошлые локальные проверки. Они не запускались повторно при создании этого документа.

Текущий сценарий сравнивает результаты на статическом рекламном задании. Он не моделирует поведение клиентов и не доказывает рост продаж. [Расширение рабочего пути](../ops/FFS_WORKFLOW_20261026.md) добавляет бэклог, независимые прогнозы, сводку решений и библиотеку карточек механизмов. Для закрытых исходных материалов предусмотрен отдельный локальный режим. Общая библиотека исполняемых сценариев остаётся гипотезой продукта; полезность внешнему владельцу проверяется отдельно.

В игровом режиме `rules/` владеет действиями и переходами. HTTP и Anchor используют эти правила с различными моделями доверия и денег. Сохраняй проверки аккаунтов и событий в соответствующих обёртках. Выделение границ не требует переписывать приложение по универсальному набору слоёв.

Public Goods задаёт вопрос о доступном другим результате и его повторном использовании. Solana требует отдельного основания: какое правило исполняет программа или какое доверие нужно участникам. Приватное статическое сравнение не требует блокчейна. Запись хэша результата не доказывает правильность расчёта.

## Основание переноса

Observed в предоставленной копии Family & Friends Store: README начинает с задачи владельцев вещей; серверные правила различают роли; тесты проверяют отсутствие закрытых полей; CLI получает внешние зависимости явно. Это инженерный пример, а не свидетельство клиентского спроса ALASHI. В исходнике есть SQL внутри core и возможное частичное выполнение записи: переносить следует полезный механизм с его границами.

Для приёмки этой инструкции проверь применение к новому сценарию: агент должен сохранить исходный результат человека, выбрать подходящий механизм и предъявить проверяемую границу вывода. Такая проверка инструкции не заменяет запуск продукта с внешним пользователем.
