# Аудит префикса промпта арены (В2, 15.11.2026)

Вопрос: позволяет ли текущая сборка промпта в arena agent попадать в кэш
провайдера (байт-идентичный префикс), и что стоит переставить.

Источник кода: arena/src/bin/agent.rs на коммите 4bbb531.

## Что хорошо (менять не надо)

- SYSTEM это константа (agent.rs:398), не мутирует между вызовами.
- Каждый вызов stateless: [system, user] без истории диалога (agent.rs:223-231);
  состояние живёт в файлах агента, не в контексте. Для кэша это лучший
  вариант из возможных.
- Волатильные суффиксы (инсайд лицензии, входящее сообщение, поручение
  владельца) добавляются в КОНЕЦ user-промпта (agent.rs:1403-1424).
- serde_json без preserve_order (arena/Cargo.toml:11): ключи состояния
  сериализуются отсортированными, «Состояние: {...» детерминировано.

## Что мешает кэшу

Сборка user-промпта (agent.rs:1394-1399):

```
{prompt}\nСостояние: {json}\nТы — фракция idx {i}.\nДоступно: {space}\n...
```

Динамическое «Состояние» стоит в середине. После него идут «Ты — фракция
idx N» и «Доступно: {space}» (меню действий, ~500-700 токенов), которые
стабильны в пределах фазы всю партию. Провайдерский кэш префикса режется
на первом изменившемся байте, то есть на «Состояние»; меню действий
пересылается полной ценой на каждом ходу.

Кандидат-перестановка (только порядок, без изменения текста):

```
{prompt}\nТы — фракция idx {i}.\nДоступно: {space}\nСостояние: {json}\n...
```

## Точные числа стоимости (из results.json usage, контрольные вызовы)

На сохранённый вызов: A0 3102.5 / A1 3068.9 входных токенов (пустая
память), H 3637.2 (со слоем памяти): +17.9% входных, -23.9% выходных
(163.8/160.0 против 123.3). Поправка к README аудита: прежние «2.7k на
решение» делили токены на 2422 решения (контроль + диагностика); здесь
деление на 2097 контрольных сохранённых вызовов.

## Почему перестановка не сделана молча

Порядок частей промпта меняет поведение модели. По правилу репозитория
и ub-mode такое изменение требует спаренного прогона. Пререгистрация:

- Дизайн: A/B на одном движке, differ только порядок строк в user-промпте
  (текущий против кандидата), те же сиды, 3 места, >= 12 сидов, руки
  идентичны текущим A-рукам (пустая память).
- Первичная метрика: входные токены на вызов (ожидание при работающем
  кэше провайдера: минус 15-25% на action/market-фазах; если у провайдера
  нет автокэша, эффект 0 и это честно фиксируется).
- Вторичная: выплата и доля parse-ошибок; сдвиг поведения сверх шума
  означает, что порядок значим для модели, и переносится отдельно.
- Бюджет: около 2 x 36 партий x ~22 вызова x ~3.1k токенов ~ 5M входных
  токенов; запуск только по решению владельца о расходе (прецедент:
  agent-context-ab, согласованные ~6.9M).
