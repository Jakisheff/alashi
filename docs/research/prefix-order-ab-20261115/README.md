# prefix-order-ab (15.11.2026)

Вопрос (из ../harness-audit-20261115/prefix-audit.md): повышает ли перенос
стабильного блока (идентичность + меню действий) вперёд динамического
«Состояние» попадания в префикс-кэш провайдера и снижает ли оплаченные
входные токены, без сдвига поведения.

## Дизайн

- 36 сидов × 2 руки × seat 0, соперники greedy+tactical, epoch 1,
  vote_weight_mode 1. Движок bin/evalgame (тот же бинарий, что в
  agent-context-ab, sha в protocol.json), glm-5.3, настройки исполнителя
  заморожены в protocol.json. Решения stateless: история не отправляется,
  промпт зеркалит agent.rs:1394-1399.
- Руки отличаются ТОЛЬКО порядком блоков внутри user-промпта:
  mid = OWNER + Состояние + «Ты — фракция idx N» + «Доступно: меню»;
  front = OWNER + «Ты — фракция idx N» + «Доступно: меню» + Состояние.
- Отклонение от пререгистрации prefix-audit.md: seat 0 × 36 сидов вместо
  3 мест × 12 сидов (переиспользование конвейера agent-context-ab,
  постоянный состав соперников; мощность по сидам, первичная метрика
  токенам от посадки не зависит).
- Воспроизведение: python3 make_protocol.py && python3 collect.py &&
  python3 analysis.py && python3 ../../harness-audit-20261115/passk_analysis.py --src . --out passk.json

## Интерпретация и перенос

1. Перестановка безопасна по поведению (выплата в шуме, illegal 36/36 у обеих рук)
   и улучшает надёжность формата (p=0.0063): перенесена в agent.rs (коммит
   рядом), арена-тесты зелёные.
2. Денежный эффект на coding-плане отсутствует: prompt_tokens не различаются,
   план не биллит по токенам. Эффект +76 кэшированных токенов на вызов
   (~5% входа) конвертируется в экономию только на pay-per-token API
   (Anthropic 1.25x запись / 0.05x чтение: 76 токенов × 24 = экономия
   входа ~5% при прочих равных).
3. Отклонение от пререгистрации prefix-audit.md: seat 0 × 36 сидов вместо
   3 мест × 12; первичная метрика от посадки не зависит.
