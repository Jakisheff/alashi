# Strategy cycle staging

Visual reference: the owner's approved RTS overview terrain and original Degenie
atlas from `experiments/alashi-watch/rts-overview/assets/`. Preserve the whole map.
The stage depicts recorded execution events for both sides of the same duel. It does not simulate model reasoning.
The user can replay a completed run; a disconnected live view freezes.

Intent: a Degenie receives a task, travels to its station, works, and returns a
checked report. Two owner teams use their own task graphs on the same shared brief.
The chief signals submission after brief checks. Creative acceptance requires
the separate host review. A completed task is not evidence of ad conversions.
Key poses: attentive idle, facing the route, arrival/work, return, accepted report.
No character carries a physical commodity in this workflow. The moving item is
a report marker attached to its carrier, removed at the home endpoint.

| Lasseter principle | Application |
| --- | --- |
| Squash/stretch | Rigid atlas body stays intact; no artificial body scaling. |
| Timing | Short preparation, fast travel, visible work, short handoff. |
| Anticipation | Facing and task label precede departure. |
| Staging | Whole map, upright A/B, fixed station labels, status beside map. |
| Follow-through/overlap | Original atlas motion retained; return settles before completion. |
| Straight ahead/pose to pose | Task stages are explicit; atlas frames interpolate the action. |
| Slow in/out | Smoothstep on both ends of each journey. |
| Arcs | Existing cubic Bezier paths, with direction derived from the tangent. |
| Exaggeration | Bright selection ring and report marker; no invented result. |
| Secondary action | Existing smoke and gaze in atlas; no unrelated idle missions. |
| Appeal | Original recognizable Degenie silhouette and face, preserved proportions. |
| Personality | Purposeful work and restrained accepted pose after checked report. |

Reduced motion holds meaningful station/home poses. At phone width the full map
remains visible, with larger semantic status cards below. A live duel and a replay
are explicitly distinguished. Numeric usage is never an animation counter.

Acceptance: desktop and phone screenshots, motion playback, failed/unknown usage
states, offline freeze, frontend build and the project's animation suite. A new
viewer's comprehension and real phone frame rate require separate observation.

Product framing, clarified by Amir: ALASHI tests owner skills and agent teams.
Advertising is the first task in the pilot, not the arena category. Other task
types need their own result contract and acceptance checks before use.

## Trading result contract

The trading graph uses the same poses and paths. Intent: finish the owner task
graph, then acknowledge a confirmed game action. The receipt journey starts
after every task has returned. Its label names PRODUCE, SELL or BUY; a tool
completion alone cannot launch it. The final accepted pose follows that journey.
All principles in the table apply unchanged. The carried marker remains a
report, not a crate or payment. Commodity handling stays in the game scene.

Timing expands short recorded calls so the order is readable. Playback seconds
are not provider latency; receipts retain the original timestamps. Parallel
independent tasks remain parallel. A receipt missing from the run creates no
receipt journey. Desktop and phone evidence is recorded with the trading-cycle
acceptance, including simultaneous work and the later receipt stage.
