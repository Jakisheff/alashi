# Команда в экономике alashi: TEST

Observed: локальное исполнение существующих правил игры. Перенос в реальную команду остаётся not_validated. Все контроллеры скриптовые; данных компаний и работников нет.

Режим `/work-simulation` использует производство и общий рынок alashi. Последствия действий и расчёт банка вычисляет существующий Rust `arena/src/bin/evalgame.rs` через `alashi-rules`. Правила игры не изменены. Предыдущий кейс библиотеки заменён игровым кейсом; исторический вариант доступен в Git на `2472cc2`.

```text
Action: произвести → запас → следующий Market: продать → казна → ранг и выплата
                                 ↑
                     общий рынок и принятые законы

План команды → решения одной фракции → квитанции движка → профиль вклада
```

## Разбор по Баумейстеру

Это применение пяти факторов из скилла владельца к alashi, а не приписывание автору модели бизнеса.

| Фактор | Что рассматриваем в игре |
|---|---|
| Последовательность | Порядок Market → Action → Law повторяется шесть раундов. Произведённый товар продаётся на следующем рынке. |
| Осмысленность | Объём продажи связывает запас с казной. Общая ценовая кривая и законы меняют результат. |
| Концептуальная схема | Фракция представляет игровой бизнес; её команда управления готовит решения. Соперники и правила образуют среду. |
| Конкретизация | В интерфейсе выбирается seed и место. Квитанции показывают принятые действия и выручку конкретных продаж. |
| Актуализация | Парное сравнение проверяет добавленный вклад. Результат формирует гипотезу о полезной компетенции. |

Экономика фракции здесь не моделирует продажи самого продукта alashi. Затраты людей и спрос клиентов в эту серию не входят.

## Четыре конфигурации

| Конфигурация | Компетенция | Доступный контекст |
|---|---|---|
| A | Базовый исполнитель, продажа одной единицы | Собственные остатки и текущая фаза |
| B | Та же базовая политика | Также публичная карта закона и право вето |
| C | Планировщик объёма продаж по запасу | Собственные остатки и текущая фаза |
| D | Тот же планировщик | Также публичная карта закона и право вето |

Планировщик является дополнительной задачей управления одной фракцией. Он не добавляет фракцию, игровые товары или дополнительные действия. В `runCycle` сначала исполняется граф локальных TEST-инструментов. Задача `review` проверяет исходный объём продажи и меняет политику. Затем готовая политика управляет полной партией через существующий `evalgame`.

Базовый исполнитель намеренно ограничен продажей одной единицы. Планировщик продаёт доступный запас. Все конфигурации производят в Action первых пяти раундов и пропускают последнюю Action: следующего рынка уже нет. При доступной карте политика голосует против налогов и эмбарго, а президент проверяет право вето. Это объявленные TEST-политики; оптимальность игры не утверждается.

Для каждой конфигурации используются seed `11, 29, 47, 83` и все три места против двух существующих `RandomBot`: 12 партий, всего 48. Режим Classic, обычный последовательный рынок, одинаковые начальные ресурсы и настройки. Соперники сохраняют свою политику и случайный поток; их действия могут измениться в ответ на новое состояние. Это сравнение последствий политики во взаимодействующей игре.

Seed фиксированы заранее и открыты. Отложенной проверки и статистического вывода о других соперниках здесь нет. Разницу считаем только внутри пары с одинаковыми seed и местом. При несовпадении условий профиль блокируется.

## Наблюдаемый результат

Observed, 18.10.2026. Значения в игровых alashi; это локальные балансы.

| Конфигурация | Средняя конечная казна | Средняя выплата из банка | Средний остаток товара |
|---|---|---|---|
| A | 56,37 | 13,50 | 6,33 |
| B | 58,33 | 13,50 | 6,33 |
| C | 114,04 | 15,00 | 0 |
| D | 117,83 | 15,00 | 0 |

Планирование объёма продаж повысило казну во всех 12 парных условиях при каждом варианте контекста. Добавление публичного контекста повысило казну в семи случаях и оставило её прежней в пяти; средняя выплата не изменилась. Казна внутри игры и выплата из банка являются разными величинами. В этой серии более высокая казна не всегда меняет ранг.

У управляемых фракций нет недопустимых действий. Для каждой партии проверяется порядок всех 18 фаз и равенство суммы выплат с рейком размеру банка. Полный повтор первой партии D воспроизводит её действия и расчёт.

Профиль для проверки: связывать произведённый запас с объёмом продажи, контролировать остаток к последнему рынку. Основание находится в парных C против A и D против B. Контекст закона проверяется отдельно в B против A и D против C. Код оценивает введённое планирование; другие компетенции не ранжировались. Не установлено, нужен ли для него новый сотрудник, обучение команды или более простой инструмент.

## Как запустить

Из корня репозитория, с текущим закреплённым Rust и Node.js не ниже 22.18:

```bash
cargo build --locked --manifest-path arena/Cargo.toml --bin evalgame
npm ci --ignore-scripts --prefix tools/agent-bootstrap
cd frontend
npm ci
npm run work:simulate
npm run check:work
npm run work:server
```

Если используется отдельный Cargo target, указать `CARGO_TARGET_DIR` либо `ALASHI_EVALGAME_BIN` с путём к собранному `evalgame`. Без бинарника прогон завершается ошибкой. Подмена расчёта скриптовой формулой отсутствует.

В другом терминале из `frontend`:

```bash
ALASHI_WORK_SIMULATION_API_TARGET=http://127.0.0.1:18715 npm run dev -- --host 127.0.0.1 --port 5183 --strictPort
```

Открыть `http://127.0.0.1:5183/work-simulation`. Кнопка выполняет новую серию всех конфигураций. JSON содержит политики и квитанции действий для всех партий. Для первой партии каждой конфигурации сохранены полные наблюдения контроллера; для остальных есть хеш трассы решений. Ошибка сохраняет предыдущий результат. Production-сборка показывает записанный TEST-прогон, повторный запуск выключен.

Локальный сервис слушает только 127.0.0.1. Он принимает фиксированный POST из локального origin; тело запроса и одновременный повтор отвергаются. Модели не вызываются. Обращений к RPC нет; кошельки не используются.

[Канонический JSON-отчёт](../../frontend/src/work-simulation/report.json) содержит SHA-256 исходников и собранного бинарника. Хеш бинарника зависит от сборки; хеш исходников позволяет проверить версию правил. Это средство воспроизведения, а не независимая аттестация исполнения.

Один прогон графов делает 16 вызовов локальных инструментов и 0 вызовов моделей; после графов выполняются 48 локальных игровых процессов. Повторное открытие завершённого журнала не повторяет задачи. Бюджет и аварийное восстановление остаются в существующем scheduler; отдельная реализация не добавлена.
